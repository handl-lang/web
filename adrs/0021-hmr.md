# Hot Module Replacement (HMR)

## Decision

1. **Components.** ┌──────────────┐     file change     ┌──────────────┐ │  handl     │  ────────────────▶  │  HmrServer   │ │  documents   │                     │  (dev tool)  │ └──────────────┘                     └──────┬───────┘ │ WebSocket ▼ ┌──────────────┐ │  HmrClient   │ │  (runtime)   │ └──────┬───────┘ │ ▼ ┌──────────────┐ │  Module      │ │  Resolver    │ │  (swap /     │ │   reload)    │ └──────────────┘
2. **WebSocket protocol.** Messages are JSON over WebSocket.
3. **Document surface.** `hmr` may appear at the document level and on individual declarations. Declaration-level settings override document-level defaults.
4. **Lifecycle.** 1. The dev server detects a file change. 2. It reloads the document, validates it, and computes a diff. 3. If any changed or removed declaration is not accepted for HMR, the server sends `hmr:full-reload` and the runtime restarts. 4. For an accepted delta: inject the new definition, and restore any `data` values.
5. **Host integration.** Hosts can extend HMR by registering custom update handlers. For example, Peregrin's host might preserve workflow execution state (event log, pending events, node fire counts) across module swaps, adding orchestration-specific semantics to the base HMR protocol.

## Why

handl documents are loaded by the module resolver and evaluated by the VM. During development, changing a document while the program is running currently requires stopping the process and starting again. This is acceptable for short-lived programs but painful for long-running ones — servers, watchers, streaming pipelines — where you want to iterate without losing in-flight state, event logs, or pending operations.
